# Codex Connect: контракт и проверка

Интеграция оборачивает отдельно установленные `codex_connect.py` и `send_ui.py`. Эти скрипты и сам Codex не входят в репозиторий. Ядро агента может работать без этой интеграции; включайте её только после задания реальных локальных путей и проверки совместимости.

## Требуемое поведение внешнего адаптера

Реализуемый контракт находится в `server/lib/codex-bridge.mjs`. Обёртка вызывает Python-адаптер через настроенный WSL, ожидает JSON от `doctor`, `discover` и `read` (для чтения передаётся глобальный `--timeout`), использует видимые сообщения и live status/pending. UI sender получает файл с UTF-8 сообщением и точный thread. Перед изменением внешних скриптов проверьте аргументы в коде и зафиксированные SHA.

Полный диапазон текущих схем требует совместимого адаптера: `--timeout` 1..60, discovery `--limit` 1..200, read `--limit` 1..20 и `--max-chars` 100..200000. Для UI действует предел **32768 байтов UTF-8**, дополнительно проверяемый до запуска; длина JavaScript-строки не заменяет размер в байтах. У старых адаптеров пределы могут быть ниже. Обновление MSI не обновляет внешние скрипты и их SHA: парное обновление и проверка нового контракта выполняются отдельно. Отказ старого CLI остаётся отказом/неизвестным исходом по фактическому этапу, а обрезанный текст не подтверждает доставку.

| Инструмент | Назначение | Что не доказывает успех |
| --- | --- | --- |
| `codex_doctor` | Доступность адаптера, backend/socket и совместимой диагностики | Доступность конкретного thread и доставку UI-сообщения |
| `codex_discover` | Поиск кандидатов; точный title является фильтром | Разрешение выбрать первый совпавший title |
| `codex_read_thread` | Видимые сообщения и живое состояние точной сессии | Возможность отправки без отдельного preflight |
| `codex_send_message` | Одна разрешённая отправка в exact idle thread | Завершение работы агентом после получения сообщения |
| `codex_delivery_status` | Сохранённый статус по receipt ID или заранее известному operation ID; при необходимости живая сверка | Повторную отправку — этот инструмент её не выполняет |

## Выбор и отправка

Используйте точный `thread_id`. Если известен только title, выполните discover и проверьте кандидатов. Одинаковые названия могут принадлежать разным сессиям. Частичный IPC-сбой одного кандидата не доказывает недоступность остальных; `thread_ids` ограничивает проверку известными UUID.

Для отправки нужны точные UUID, title и cwd, статус `idle`, отсутствие pending requests и неподтверждённых submissions, а также разрешение пользователя на передачу полного текста. Код выполняет проверки перед подготовкой и перед UI-вызовом. Дополнительные поля адаптера `pending_state_known`, `pending_request_count` и `unconfirmed_submission_count`, если они присутствуют, тоже проверяются: неизвестность не подменяется пустым массивом.

Новый клиент должен заранее сохранить стабильный `operation_id` и передать его в `codex_send_message`. Допустимы 8..128 ASCII-букв, цифр, `_` и `-`, первый символ — буква или цифра. Поле пока необязательно для совместимости прежних клиентов, но без него клиент не имеет заранее известного ключа восстановления потерянного ответа. После ответа сохраняйте также `receipt_id`.

Квитанция атомарно сохраняется **до проверки скриптов и первого IPC-чтения**. Она связывает ID операции с UUID, title, cwd и хешем текста. Повтор того же ID возвращает сохранённый результат; изменение любого из этих полей с тем же ID отклоняется. Даже доказанно неотправленная попытка с прежним ID не запускается повторно. Новая разрешённая попытка после устранения подтверждённого preflight-отказа получает новый ID.

Дедупликация одинакового текста опирается на стабильный UUID сессии: переименование title или изменение cwd не разрешает повтор. Для совпадающей современной привязки новый ID может стать дополнительным ключом той же квитанции. Для старой квитанции, изменённой привязки или известного старого UI-хеша создаётся отдельная терминальная `not_sent_duplicate` с `deduplicated_by_receipt_id`; исходная квитанция не меняется. Новое имя операции не обходит блокировку неизвестной доставки.

`queued`, успешный запуск UI-скрипта или завершение процесса не означают доставку. Только обнаруженный новый точный user turn подтверждает её. `observed` относится к доставке сообщения, а не к выполнению поручения. `already_observed` может означать, что такой текст уже найден до отправки: новый UI-вызов тогда не выполняется. Не представляйте это как доказательство новой доставки.

Сравнение текста допускает только нормализацию `crlf_to_lf`: CRLF и LF считаются одинаковыми. Все остальные пробелы, регистр, обратные слеши и одиночные CR сохраняют значение; trim и преобразование путей не выполняются. Хеш в привязке operation ID вычисляется по исходному тексту без нормализации.

## Неизвестный результат

Фазы `prepared`, `pending_send`, `outcome_unknown` и неизвестные незавершённые фазы блокируют новую отправку в тот же thread. Квитанция содержит текущий `stage`, `last_completed_stage`, `delivery_outcome`, время обновления и безопасный код ошибки с этапом/длительностью. Сырой вывод UI, stderr и текст сообщения в журнал ошибок не записываются.

| Фаза/исход | Значение |
| --- | --- |
| `prepared` / `pending` | Операция сохранена, окончательный результат ещё не установлен |
| `not_sent_preflight_failed`, `not_sent_preflight_changed` / `not_sent` | Проверка остановилась до запуска UI sender; квитанция доступна и при тайм-ауте первого чтения |
| `not_sent_blocked` / `not_sent` | Эту попытку не отправляли, но другой неизвестный исход в том же thread требует сверки |
| `not_sent_duplicate` / `not_sent` | Новый ID привязан к текущему запросу, но старый текст уже защищён от повтора; UI не вызывался, `retry_safe=false` |
| `not_sent_ui_preflight` / `not_sent` | Полный результат совместимого UI sender явно подтвердил отсутствие Submit |
| `not_sent_ui_staged` / `not_sent` | Submit не выполнялся, однако подготовленный черновик сохранён; `retry_safe=false` |
| `pending_send`, `outcome_unknown` / `unknown` | UI-процесс мог выполнить отправку; повтор запрещён до сверки |
| `observed` / `delivered` | Найден единственный новый полный user turn со временем не раньше запуска отправки |
| `already_observed` / `already_present` | Текст уже обнаружен до отправки; новый UI-вызов не выполнялся |

После потери ответа вызовите `codex_delivery_status` с исходным `operation_id`. Можно использовать `receipt_id`; если переданы оба ID, они обязаны обозначать одну запись. Отсутствующая операция возвращает `not_found` и `delivery_outcome=unknown`: это не доказательство, что задержанный исходный запрос не будет принят.

Во время занятой блокировки status по умолчанию сразу возвращает сохранённый этап, без ожидания отправки или IPC. `refresh=false` всегда читает только квитанцию. `refresh=true` явно выполняет чтение и сверку неизвестной доставки даже при оставшейся блокировке; UI не вызывается. Доказанно неотправленные операции остаются терминальными и возвращаются из квитанции: более позднее чужое сообщение не приписывается такой попытке. Наличие lock не доказывает, что владелец всё ещё работает. Для неизвестного текущего pending возвращается `null`, а не пустой список.

Discovery по явным UUID сохраняет `pending_state_known`, оба pending/submission-счётчика и `observation` адаптера. Status возвращает текущие данные отдельно от сохранённой квитанции: `current_pending_state_known`, `current_pending_request_count`, `current_unconfirmed_submission_count` и `current_observation`. При чтении только квитанции или недоступном IPC эти текущие поля равны `null`. Состояние runtime `idle` само по себе не означает известную пустую очередь.

Сверка может подтвердить user turn, но не суметь записать обновление из-за lock или ошибки хранения. В этом случае `receipt_persisted=false`; это поле нельзя игнорировать. При ошибке финальной записи прежняя сохранённая запись остаётся защитой от повторной отправки. Чужие или повреждённые блокировки автоматически не удаляются.

После тайм-аута UI-процесса результат остаётся неизвестным даже при пустом composer и отсутствии сообщения в текущем хвосте. Только полный нетаймаутный ответ совместимого UI sender с `outcome=not_sent` и `submit_attempted=false` допускает классификацию его preflight/staging-отказа как неотправленного. Старую квитанцию с недостаточным baseline/time, обрезанный текст или несколько совпавших новых turns нельзя назвать подтверждением новой доставки.

## Сохранённые квитанции старых версий

Версия 0.3.2 учитывает ранее сохранённое `owner_resolution.action=allow_new_distinct_messages` у проверяемой старой записи без современного operation ID. Решение должно иметь согласованные дату, исходную фазу и сохранённое покрытие истории. Это позволяет новое отличающееся сообщение при свежем успешном preflight; неизвестный исход прежнего сообщения остаётся неизвестным. Поле ответа `legacy_receipt_compatibility=owner_accepted_unknown` объясняет применённую совместимость.

Начиная с 0.3.3, отсутствие необязательного legacy-хеша и явный JSON `null` одинаково означают неизвестный дополнительный хеш. Они не добавляют alias и не отменяют запрет повтора исходного сообщения. Любое ненулевое значение обязано быть корректным SHA-256. Для старой подтверждённой UI-фазы собственный `observed_message_sha256` остаётся обязательным и не может быть `null`.

Полная старая запись `observed_with_ui_line_feed` с доказательством завершённого хода из `live_tail` получает `legacy_receipt_compatibility=ui_line_feed_observation`. Она сохраняет свою фазу и не превращается в современное `observed=true`. Известные исходный и UI-хеши расширяют только запрет повтора, а не правило подтверждения доставки. Неполные, несогласованные или современные записи не получают это исключение. Новый инструмент сброса блокировки не добавлен.

Символьные `ui_result.reason` и `ui_result.error_code` сохраняются только в ограниченном формате ASCII-кода. Текст исключений, содержимое черновика и stderr через эти поля не передаются.

## Приёмка на конкретной установке

1. Проверить doctor и configured SHA внешних скриптов.
2. Прочитать точный известный thread по UUID.
3. В разрешённой тестовой сессии проверить idle, пустой pending и отсутствие черновика.
4. Заранее сохранить operation ID и один раз отправить уникальное тестовое сообщение по явному поручению пользователя.
5. Получить квитанцию с наблюдаемым новым user turn, проверить этапы и адресата.
6. Повторно прочитать статус по operation ID и receipt ID и убедиться, что новой отправки нет.
7. На синтетическом стенде прервать ответ до и после Submit, перезапустить мост и проверить восстановление того же ID, отсутствие дубликата, быстрый status во время долгой операции и сохранность чужого lock.

Обычный CI использует синтетические ответы и не выполняет этот live-сценарий. UI sender зависит от доступной пользовательской desktop-сессии и установленного клиента. Поддержка resume/steer/interrupt/approval не заявлена этими пятью инструментами.
